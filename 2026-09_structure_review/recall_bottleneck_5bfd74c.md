# Recall のボトルネック整理(living_agent 5bfd74c)

- 対象コード: `living_agent` の `experiments` ブランチ `5bfd74c`(2026-09-24)
- データ: 2026-09-23〜24 の実際の `memory.db`(Memory 300件。ステラ148件、うち recall_text を持つもの53件)
- 確認日: 2026-09-25
- この文書は現状の整理と改善案の比較だけ。リポジトリのコードは変更していない。

## 1. 今の Recall の仕組み

`ContextBuilder.build_from_text` が、応答する住人ごとに1回 `MemoryRecallService.recall` を呼ぶ。外部入力に2人とも応答するときは、2回が順番に走る(並列ではない)。実行ロックを持ったまま走るので、その間は他のターンも待つ。

`recall` は住人の Memory 全件を1件ずつ見る。

1. `recall_enabled` が偽のもの、`recall_text` がないものは飛ばす(自分の発話・Thought・Decision・Lossy置換後の Memory はここで対象外になる)。
2. 検索対象テキストを作る。renderer があると `PerceptionRenderer.recall_search_text` を使う。中身は次の3つを改行でつないだもの。
   - `recall_text`(要約。平均45文字)
   - `render_memory` の結果(「シリカが「…」と話した。」のように**発話の原文をまるごと含む**)
   - 相手の既知名
3. `_common_text_score(入力文, 検索対象テキスト)`:入力文の部分文字列(3文字以上)を長い順に取り出し、検索対象に含まれていて、既に採用した部分と重ならなければ、その長さを加点する。
4. `_recall_key_score`:recall_keys が入力文に含まれていれば、その長さを加点する。
5. 合計点の上位5件を、経験した順に並べて返す。

## 3. どこに時間がかかっているか

Memory 5000件、入力213文字、renderer あり(現行)でプロファイルを取った(プロファイラの分だけ全体は遅くなっている)。

| 処理 | 時間 | 割合 |
| --- | ---: | ---: |
| `_common_text_score` 全体 | 32.1秒 | 約98% |
| └ 採用済み範囲との重なり判定(`any(...)`、約4000万回) | 11.9秒 | |
| 他者認知の SQLite 読み込み(`EntityPerceptionRepository.get`、4162回) | 0.7秒 | 約2% |

原因は大きく2つ。

**(1) `_common_text_score` の計算量**
- 入力長を L とすると、部分文字列を L²/2 個ほど作り、1つずつ `in` で検索し、さらに採用済みの範囲すべてと重なりを比べている。
- 入力長の2乗 × Memory件数で増えるので、住人の長い発話を入力にすると急に重くなる。

**(2) 検索対象テキストが約5倍に伸びた(5bfd74c での悪化の主因)**
- renderer なしでは `recall_text`(平均45文字)だけが対象だった。今は発話の原文も加わって、平均231文字になった。
- `in` 検索が長い文字列に対して走るので、そのぶん遅い。

**訂正:前回レビューの見立て**
構造レビューでは「悪化の主因は Memory ごとの SQLite 接続で、1度だけ読めば多くは戻せる」と書いたけど、実データで測ると違っていた。

| 5000件・213文字 | 時間 |
| --- | ---: |
| 現行(renderer あり) | 15.56秒 |
| renderer あり+他者認知をキャッシュ | 14.47秒 |
| renderer なし | 11.34秒 |

SQLite をやめても戻るのは約1秒。残りの約3秒は、検索対象テキストが長くなったことによるもの。

## 4. 想起される内容への影響(速度とは別の論点)

検索対象に発話の原文が入ったことで、何が想起されるかも変わっている。シリカの発話27回を入力にして、その時点までのステラの Memory で想起を比べた(ステラ側だけの小さいサンプルなので、傾向の参考程度)。

- renderer あり/なしで、想起される5件の重なりは平均36%(Jaccard係数)。半分以上が入れ替わっている。
- 想起された Memory のうち、住人同士の発話から作られたものの割合は、renderer なしで 101/132(77%)、renderer ありで 124/132(94%)。
- 原文には「ふふっ」「ステラ」「〜ですね」などの口癖や呼び方が含まれる。そのため、話の内容より言い回しが近い住人同士の発話が選ばれやすくなっている可能性がある。会話がまとまっていく傾向との関係は、この数字だけでは分からない。

## 5. 改善案

| 案 | 内容 | 想起結果 | 仕様の判断 | 効果(5000件・213文字) |
| --- | --- | --- | --- | --- |
| A. スコア計算を同じ結果のまま高速化 | 開始位置ごとに「Memory に含まれる最長の長さ」を先に求め、重なり判定をバイト配列に置き換える。部分文字列は短いものも必ず含まれるので、長い順・左から順に選ぶ現行の結果と一致する。 | 変わらない | 不要 | 15.55秒 → 1.32秒 |
| B. 他者認知を Recall 1回につき1度だけ読む | 観測者ごとの既知名を先に辞書へ読み、Memory ごとの SQLite 接続をなくす。 | 変わらない | 不要 | A と合わせて 0.98秒 |
| C. 検索対象テキストを見直す | 検索対象を「recall_text+既知名」に戻す(表示名の置き換えは `render_recall_text` で済む)。または、原文を含める今の形を正式な仕様にする。 | 変わる | 必要 | renderer なし相当まで短くなる(A と合わせると1秒未満) |
| D. 入力文の扱いを決める | 入力の長さに上限を設ける、要約してから検索する、など。 | 変わる | 必要 | 入力長の2乗で効く |
| E. 索引を持つ | 文字3-gramの転置索引を Memory 追加時に更新し、共通部分のない Memory を最初から除く(A と組み合わせれば結果は変わらない)。スコア自体を n-gram 数で近似すると、結果が変わる。 | 除外だけなら変わらない | 近似にするなら必要 | Memory 件数が増えるほど効く |

- A の試作は、実データの入力×検索対象とランダムな文字列、あわせて9400組で現行と結果が一致した。5000件の Recall 4通り(入力2種類 × renderer あり/なし)でも、想起される5件と順番が一致した。
- 455文字の入力では、現行 71.25秒 → A のみ 4.06秒。
- ついでに見つけたこと:`_common_text_score` の「昨日」を除外する分岐は、最短の長さが3文字なので2文字の「昨日」がそもそも候補にならず、一度も使われていない。関連して、`MemorySummarizer` は recall_keys に「昨日」などを入れないよう指示している。

## 6. 決めたいこと

1. **検索対象に発話の原文を含めるか(案C)。** 速度だけでなく、何が想起されるかに直接効く。他者認知(名前の置き換え)のために原文を含めたのか、原文でも検索できるようにする意図だったのかで、判断が分かれる。
2. **A と B を先にやるか。** 想起結果が変わらないので、仕様の議論とは切り離して進められる。
3. **入力文の扱い(案D)。** 住人の長い発話をそのまま検索に使い続けるか。
4. **Recall の対象そのもの。** 自分の発話・Thought・Lossy置換後の Memory を対象外のままにするか(構造レビューの別の指摘)。
